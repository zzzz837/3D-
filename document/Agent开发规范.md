## Agent开发规范

以下内容只需要 Agent 看就行了。如果你是人类，可以不看。

### 适用规模说明

> **本范式主要适用于大规模 Version**：需求点数量 ≥ 5，存在明显可并行子任务，或代码依赖复杂、需要多个 SubAgent 并行开发。  
> **小规模 Version**：需求点少、依赖简单、预估工作量小，可由单个 MainAgent 独立完成开发与测试，无需拆分 Stage/SubStage。  
> 无论规模大小，都必须遵守"问题清单（含置信度分级与置顶区/自决区）""零猜测""零上下文验收""新功能强制单元测试 + 启动测试"原则；大规模 Version 还必须额外遵守 Stage/SubStage 拆分与 SubAgent 调度规范。

---

### 1. 核心思想

#### 1.1 基础思想：Version-Stage 拆分与并行

- 每个 **Version** 承载一组大的需求，使用语义化版本号（如 `v1.2.0`）。
- 将 Version 拆分为多个 **Stage**，Stage 之间按**代码依赖关系**或业务顺序串行执行。
- 每个 Stage 内部拆分为多个 **SubStage**，SubStage 之间必须尽量独立，并可由多个 SubAgent 并发开发。
- SubAgent **之间不允许直接沟通**；所有共享信息、接口契约、依赖关系必须由 MainAgent 在设计阶段提前写清楚。
- 每个 Stage 完成后执行**增量系统测试**；Version 全部完成后执行**全量系统回测**。
- SubStage 失败时最多重试 3 次；若仍失败，由 MainAgent 暂停当前 Stage 并重新规划。

#### 1.2 核心思想一：事前零猜测（问题清单驱动，含置信度自决）

> **在正式开始每一个 Version 或 Stage 的开发之前，必须列出所有不确定点，并按置信度分级处理。禁止带着未记录的隐式假设开发；也禁止把 MainAgent 有把握判断的问题都推给用户。**

- 所有不确定问题必须写入 `问题清单.md`，**无论最终是否需要用户回答**。写入问题清单是透明度和可追溯性的强制要求，不是"要不要问用户"的判断。
- **置信度自决规则**：MainAgent 对每个问题给出建议方案后，必须评估自身对该方案的置信度：
  - **≥ 90% 置信，且不涉及重大技术路线分歧**：直接采用建议方案，标记为 **"自决"**，写入问题清单的 **自决区**，不阻塞开发。必须同时说明自决理由（例如：Python reference 已有明确对应实现、Modbus 协议文档已定义、既有代码已建立清晰约定、Qt/CMake 官方推荐做法等）。
  - **< 90% 置信 或 存在重大技术路线分歧**：标记为 **"待用户确认"**，写入问题清单的 **置顶区**（文件最上方），阻塞开发，直到用户明确答复。
- "重大技术路线分歧"的典型判定：多种方案对架构、性能、可维护性影响显著不同；涉及尚未在本仓库沉淀过约定的领域；涉及硬件/协议/外部依赖的不可逆决策等。
- 问题清单可以经过多轮问答，**所有"待用户确认"问题关闭后**，才允许进入设计或开发；"自决"问题不阻塞流程。
- 问题清单中的每个问题必须附带建议方案/说明与风险预警，不能把"裸问题"甩给用户。

#### 1.3 核心思想二：事中/事后不确定性追加

> **开发或验收过程中，如果 MainAgent 或 SubAgent 遇到任何不确定性，也必须追加到 `问题清单.md`，按 1.2 的置信度自决规则处理：≥ 90% 置信直接自决写入自决区；< 90% 或路线分歧写入置顶区并暂停等待用户答复。**

- 不确定性包括：临时决定、留空项、接口歧义、边界条件不明、测试期望不明、验收标准不明确等。
- 新增问题关闭后（无论自决还是用户答复），MainAgent 必须判断是否需要同步更新设计文档、验收文档、测试用例或完成报告。

#### 1.4 核心思想三：零上下文闭环

> **任何开发与验收文档都必须允许一个全新的 Agent 在没有对话历史、没有口头约定的情况下，独立理解、执行和判断结果。**

- 开发前：Stage 设计文档和 SubStage 任务书必须满足“零上下文可开发”。
- 验收前：Stage/Version 验收文档必须满足“零上下文可验收”。
- 收尾时：完成报告必须能追溯需求、问题清单、设计文档、实际改动和测试结果。

### 2. 角色与职责

| 角色 | 职责 |
|------|------|
| **MainAgent** | 1. 拆分 Version 为 Stage，并按依赖关系排序。<br>2. 将每个 Stage 拆分为可并行的 SubStage。<br>3. 编写并自行审核 Stage 设计文档、SubStage 任务书和验收文档。<br>4. 分发 SubStage 给 SubAgent。<br>5. 管理问题清单、接口契约、测试计划、完成报告和验收记录。<br>6. 处理 SubAgent 反馈的不确定性，并追加到问题清单。<br>7. 协调测试、汇总结果、处理重试与重新规划。 |
| **SubAgent** | 1. 接收已拆分好的 SubStage 任务。<br>2. 严格按任务书开发，不自行扩大或改变任务边界。<br>3. 开发中遇到任何不确定性时立即停止并报告 MainAgent。<br>4. 完成开发后按任务书自测，并报告结果。<br>5. 禁止与其他 SubAgent 直接沟通；需要共享的信息由 MainAgent 统一提供。 |
| **验收 Agent / 验收者** | 1. 只依据验收文档、设计文档、完成报告和仓库当前状态进行验收。<br>2. 不依赖本轮对话历史或口头解释。<br>3. 对每条验收项给出通过/失败/阻塞结论，并记录证据。<br>4. 如验收标准不清，必须要求 MainAgent 补充文档，而不是自行猜测。 |

### 3. 开发流程

#### 3.1 Version 规划（含问题清单）

1. **确定大需求组**：例如“订单系统性能优化”，并分配语义化版本号。
2. **创建 Version 级问题清单**：
   - 在 Version 文件夹下新建 `问题清单.md`，按 6.2 划分 **置顶区** 与 **自决区**。
   - MainAgent 详细阅读需求，列出所有不确定点：接口定义、依赖组件、性能指标、边界条件、兼容要求、验收方式等。
   - 每条问题必须包含问题描述、建议方案/说明、风险预警、置信度、分区归属；必要时给出备选方案。
   - **所有"待用户确认"问题（置顶区）全部关闭前**不允许进入拆分；"自决"问题不阻塞流程。
3. **拆分为小需求点**：
   - 优先按代码依赖关系解耦。
   - 如果无法完全解耦，则保留必要依赖，并用该依赖决定 Stage 串行顺序。
   - 可按业务顺序划分，但必须保证前后 Stage 之间接口稳定。
4. **排列 Stage 顺序**：
   - 将所有小需求点按依赖关系排序。
   - 切分成若干连续 Stage，Stage 之间串行执行。
5. **建立 Version 级验收框架**：
   - 在规划阶段就确定最终 Version 如何验收。
   - 若存在硬件、外部系统或人工验证依赖，必须提前标注“需用户配合”。

#### 3.2 Stage 内部规划（含子问题清单）

每个 Stage 开始前，必须重复问题清单流程：

1. **创建 Stage 级问题清单**：
   - 在对应 Stage 文件夹下新建 `问题清单.md`，或追加到 Version 主问题清单中；建议独立。按 6.2 划分 **置顶区** 与 **自决区**。
   - MainAgent 针对该 Stage 列出所有需要澄清的细节：输入输出格式、跨 SubStage 契约、异常处理策略、测试方式、验收证据等。
   - 每条问题按置信度分级：≥ 90% 置信直接自决入自决区，< 90% 或路线分歧入置顶区。
   - **置顶区问题全部关闭后**才允许拆分 SubStage。
2. **拆分 SubStage**：
   - 将 Stage 拆分为无相互开发依赖的最小工作单元。
   - 一个 SubAgent 可以被分配多个 SubStage，但每个 SubStage 的任务书必须自足。
   - 所有跨 SubStage 共享的数据、接口、文件路径、字段名、生命周期、错误处理策略，必须由 MainAgent 在 Stage 设计文档中写清楚。
3. **编写 Stage 设计文档**：
   - 必须满足第 6.1 节“零上下文可开发”标准。
   - 必须包含 SubStage 列表、输入/输出、接口契约、禁止事项、依赖前置条件、预期测试用例。
4. **编写 Stage 验收文档**：
   - 必须满足第 6.3 节“零上下文可验收”标准。
   - 验收文档可以是独立 `验收文档.md`，也可以是 Stage 设计文档中的独立章节；大规模 Version 建议独立成文。
5. **MainAgent 自行审核**：
   - 设计文档通过“零上下文可开发”自检后，才允许分发 SubStage。
   - 验收文档通过“零上下文可验收”自检后，才允许进入实际开发。

#### 3.3 执行流程（单 Stage，含开发中问题追加）

1. **MainAgent 分发 SubStage**：每个任务必须明确输入、输出、验收标准、禁止事项、相关文件路径和跨 SubStage 契约。
2. **SubAgent 开发**：
   - 按任务书完成代码实现。
   - 开发中若遇到任何不确定性，立即停止并报告 MainAgent。
   - MainAgent 将问题追加到当前 Stage 的 `问题清单.md`，按 1.2 置信度规则处理：≥ 90% 直接自决并写入自决区，SubAgent 恢复开发；< 90% 或路线分歧写入置顶区并提交用户，待用户答复后恢复开发。
   - 问题关闭后，MainAgent 同步更新必要文档，再恢复开发。
3. **SubAgent 自测**：
   - 执行任务书中要求的单元测试、构建、静态检查或人工检查步骤。
   - 报告必须包含执行命令、结果、失败信息或无法执行原因。
4. **MainAgent 汇总并集成**：
   - 等待所有 SubStage 完成。
   - 处理合并冲突、接口偏差和文档同步问题。
5. **Stage 测试**：
   - 执行全量单元测试（新功能/较大更新必须包含针对本 Stage 新增逻辑的单元测试用例，见第 4 节强制要求）。
   - 执行当前 Stage 新增/影响功能的增量系统测试。
   - 执行 **启动测试**（新功能/较大更新强制）：实际启动应用，走一遍本 Stage 引入的核心操作路径，观察崩溃/异常日志/UI 异常；结果写入完成报告。
   - 若测试失败，定位到具体 SubStage 并重试，最多 3 次。
6. **Stage 验收**：
   - 按 Stage 验收文档逐项验收。
   - 每条验收项必须记录通过/失败/阻塞，以及证据来源（命令输出、文件路径、截图说明、人工操作记录等）。
   - 若验收文档本身不清晰，必须先补文档再验收，禁止靠对话历史补全。
7. **Stage 完成前交付物**：
   - Stage 设计文档。
   - Stage 验收文档。
   - Stage 完成报告（须包含启动测试证据章节，如为豁免场景须写明豁免理由）。
   - 测试报告或完成报告中的测试章节（单元测试执行命令与结果、启动测试操作路径与观察记录）。
   - 最终问题清单，包含所有已解答的问题、开发中追加的问题，以及所有自决问题。

#### 3.4 Version 完成后的收尾

- 所有 Stage 完成后，执行完整的全量系统测试。
- 按 Version 级验收文档执行全量验收，覆盖所有历史功能和本次 Version 新增/影响功能。
- 检查所有 Version/Stage 问题清单，确保无未关闭问题。
- 检查所有 Stage 设计文档、验收文档、完成报告是否互相一致。
- 产出 Version 总结报告：Stage 汇总、全量系统测试结果、验收结论、语义化版本号、变更日志、问题清单归档。
- 为 Version 打上语义化版本号 tag（如 `v2.1.0`）。

### 4. 测试与验收策略总结

> **强制要求（新功能 / 较大更新）**：
>
> 凡属于以下任一情形，均视为"新功能 / 较大更新"，必须同时进行 **单元测试** 与 **启动测试**，缺一不可，禁止仅凭编译通过就报告任务完成：
>
> - 新增功能模块、对话框、数据流、协议实现、新的 Modbus 寄存器读写路径。
> - 新增文件 ≥ 3 个，或影响文件 ≥ 5 个。
> - 涉及信号槽新连接、跨线程通信、OpenGL/QChart/QML 渲染改动。
> - 触及"Critical Recurring Bugs"清单中列出的任一模块（sendCommandAndStopUpload、GL_UNPACK_ALIGNMENT、QChart 轴序、信号链重入等）。
>
> **强制项：**
>
> 1. **单元测试**：对新增或修改的核心逻辑必须编写 gtest / QtTest 单元测试用例，覆盖正常路径与至少一个边界/异常路径；测试必须实际执行并通过。
> 2. **启动测试**：完成开发后必须实际启动 `TactileSense.exe`（或对应子应用），走一遍新功能核心操作路径，验证程序能正常启动、进入相关功能、执行核心操作无崩溃、无异常日志、UI 无明显异常。启动测试证据（截图说明、日志片段、操作记录）必须写入完成报告。
>
> **小规模修改**（≤ 2 个文件、纯 bug fix、无新增数据流）可豁免启动测试，但仍鼓励在有条件时补上；单元测试若涉及既有测试覆盖的逻辑，必须跑通对应的既有测试。

| 类型 | 触发时机 | 范围 | 环境 | 负责人 | 输出 |
|------|----------|------|------|--------|------|
| 单元测试（全量） | 每个 Stage 结束后；**新功能/较大更新强制** | 所有单元测试用例 | 共享测试环境 | MainAgent | 测试记录/完成报告测试章节 |
| 系统测试（增量） | 每个 Stage 结束后 | 当前 Stage 新增或影响的功能 | 共享测试环境 | MainAgent | 测试记录/完成报告测试章节 |
| **启动测试** | **新功能/较大更新完成后强制** | **实际启动应用，走一遍新功能核心路径，观察崩溃/日志/UI 异常** | **本机开发环境（连接或模拟真实硬件）** | **MainAgent** | **启动截图说明、异常日志片段、操作步骤记录，写入完成报告** |
| Stage 验收 | 每个 Stage 测试通过后 | 当前 Stage 的验收项 | 共享测试环境或文档指定环境 | MainAgent 或验收 Agent | Stage 验收记录 |
| 系统测试（全量） | Version 所有 Stage 结束后 | 整个系统 | 共享测试环境 | MainAgent | Version 测试记录 |
| Version 验收 | 全量系统测试后 | 本 Version 完整交付范围 | 文档指定环境 | MainAgent 或验收 Agent | Version 验收结论 |

> **注意**：只有一个 MainAgent 负责完整测试协调，所有测试在同一个共享环境中串行执行，避免环境冲突。若验收需要硬件、外部系统或人工操作，验收文档必须提前写明依赖和替代验证方式。
>
> **启动测试的最低通过标准**：
>
> - 应用无崩溃启动，主窗口正常显示。
> - 新功能入口可点击/触发，进入后无立即崩溃。
> - 核心操作路径（例如"打开对话框 → 输入参数 → 提交 → 观察响应"）至少完整走一遍且无异常。
> - `qDebug/qWarning/qCritical` 输出无与本次改动相关的报错；spdlog 日志无 ERROR 级别记录。
> - 如无法在本机启动（缺硬件、需真实设备），必须在完成报告中明确说明"启动测试阻塞原因"并追加到 `问题清单.md` 的置顶区。

### 5. 异常处理与重规划

- **SubStage 失败重试**：
  - 由 MainAgent 通知对应 SubAgent 重试，最多 3 次。
  - 重试前可要求 SubAgent 提供问题分析。
- **3 次失败后**：
  - MainAgent 暂停当前 Stage。
  - 分析失败原因：任务拆分不合理、依赖遗漏、接口契约不完整、测试/验收标准不清、SubAgent 能力不足等。
  - 重新划分 SubStage，或重写整个 Stage 分配方案。
- **不确定性导致暂停**：
  - 开发或验收中遇到未定义行为，必须追加问题清单，按 1.2 置信度规则处理：≥ 90% 置信自决入自决区并恢复开发；< 90% 或路线分歧入置顶区并寻求用户解答。
  - 问题关闭后（自决或用户答复），MainAgent 必须同步更新相关设计文档、验收文档和测试项。
- **验收失败**：
  - 若实现不满足验收标准，定位到相关 SubStage 修复。
  - 若验收标准不完整或不可执行，先修订验收文档并重新自检，再继续验收。
- **禁止事项**：
  - SubAgent 不得擅自修改任务边界。
  - 验收者不得用对话历史替代验收文档。
  - 不得把无法执行的验收项默认为通过。
  - 不得跳过启动测试就把新功能/较大更新标记为完成。

### 6. 文档与门禁要求

| 工件 | 产生时机 | 格式 | 包含内容 |
|------|----------|------|----------|
| **Version 问题清单** | Version 规划阶段开始前 | Markdown | Version 需求不确定性、多轮问答记录。必须分 **置顶区**（待用户确认）与 **自决区**（≥ 90% 置信自决）。每条问题必须附带建议方案/说明、风险预警、置信度评估（见 6.2）。 |
| **Stage 问题清单** | 每个 Stage 开始前，开发/验收中持续追加 | Markdown | Stage 特有不确定性、开发和验收中追加的问题、最终答复。必须分 **置顶区** 与 **自决区**。每条问题必须附带建议方案/说明、风险预警、置信度评估（见 6.2）。 |
| **Stage 设计文档** | Stage 开发前 | Markdown | SubStage 列表、输入/输出、跨 SubStage 契约、接口定义、禁止事项、预期测试用例。必须满足"零上下文可开发"（见 6.1）。 |
| **Stage 验收文档** | Stage 开发前，最晚不得晚于分发 SubStage 前 | Markdown | 验收范围、环境、前置条件、验收项、操作步骤、期望结果、证据要求、阻塞处理。必须满足"零上下文可验收"（见 6.3）。 |
| **Stage 完成报告** | Stage 测试和验收通过后 | Markdown | 实际完成情况、改动文件、接口变化、单元测试结果、**启动测试证据（新功能/较大更新强制，含操作路径、截图说明、日志片段）**、验收结果、已知问题、问题清单闭环状态。 |
| **Version 验收文档** | Version 规划阶段或首个 Stage 前 | Markdown | Version 级全量验收范围、关键业务路径、跨 Stage 集成检查、硬件/外部依赖、通过标准。 |
| **Version 总结报告** | Version 全量测试和验收后 | Markdown | 所有 Stage 汇总、全量系统测试结果、Version 级启动测试结果、Version 验收结论、语义化版本号、变更日志、问题清单归档（含所有自决问题）。 |

#### 6.1 “零上下文可开发”标准

> **核心要求：任何 Stage 设计文档或 SubStage 任务书，都必须让一个全新的 session 仅凭该文档就能理解目标并直接开始开发。**

**必须包含的内容：**

1. **背景与目标**：用 1-3 句话说明本 Stage/SubStage 要解决什么问题，达到什么状态。不得使用“如之前讨论的”“按照需求”等引用性描述。
2. **当前代码状态**：说明相关文件/模块现在的状态；涉及具体文件时给出相对路径，必要时给出行号。
3. **完整接口契约**：所有跨 SubStage 或跨模块的接口、数据结构、枚举值、常量、字段名、生命周期和错误处理策略必须完整定义。
4. **输入与输出**：明确任务输入来自哪里，输出写到哪里，产物格式是什么。
5. **验收标准**：明确完成判定条件，例如哪些测试必须通过、哪些接口必须可调用、哪些行为必须可观测。
6. **禁止事项**：明确列出本 SubStage 不应触碰的模块、文件或行为。
7. **依赖前置条件**：如果依赖另一个 SubStage 的产物，必须说明产物位置、格式和可用条件。

**审核自检问题：**

- 一个从未参与本 Version 讨论的 Agent，读完文档后是否知道要改哪些文件？
- 文档中是否有任何需要对话历史才能理解的表述？
- 接口定义是否完整到可以直接写代码？
- 验收标准是否可以由 SubAgent 独立自测？
- 禁止事项和依赖边界是否足够明确，能避免越界修改？

#### 6.2 问题清单的"附建议/说明"标准（含置信度分级）

> **核心要求：问题清单中的每一条问题，MainAgent 必须同时给出至少一个建议方案或说明，并按置信度分级处理，作为用户判断或自决依据。**

**必须包含的内容：**

1. **问题描述**：明确说明不确定点，并尽量定位到具体文件、模块或行号。
2. **建议方案或说明**：MainAgent 必须基于现有代码和上下文给出推荐答案或说明性意见。
   - **鲁棒性优先**：优先选择失败模式可控、行为可预测、边界明确的方案。
   - **可测试性优先**：方案必须能写出明确测试或验收用例。
   - **价值导向**：解决实际问题，不加入无用抽象或过度设计。
   - **不考虑工期**：开发由 Agent 执行，工期不是约束条件；禁止以"简单快速""实现成本低"作为推荐理由。
3. **风险预警**：提前列出已知风险，特别是可能导致任务无法闭环的风险；无法由 Agent 侧规避的风险必须标注"需用户决策"。
4. **备选方案**：当存在多条合理路径或推荐方案风险较高时，给出 1-2 个备选方案，并从鲁棒性、可测试性、风险三个维度对比。
5. **置信度评估**：MainAgent 必须给出对建议方案的置信度（百分比或高/中/低），并据此归类：
   - **≥ 90% 置信 且 不涉及重大技术路线分歧** → 归入 **自决区**，写明"自决理由"（例如：Python reference 已有明确实现、Modbus 协议已定义、既有代码约定明确、Qt/CMake 官方推荐做法等），不阻塞开发。
   - **< 90% 置信 或 存在重大技术路线分歧** → 归入 **置顶区**，阻塞开发直到用户答复。
6. **分区归属**：问题清单必须显式划分 **置顶区（待用户确认，阻塞开发）** 与 **自决区（≥ 90% 置信，已自决，不阻塞开发）** 两个章节，**置顶区必须在文件最上方**，方便用户第一时间看到需要决策的事项。所有问题——无论是否需要用户回答——都必须写入其中之一，禁止"心里知道但不落文档"。

**问题清单推荐结构：**

```markdown
# 问题清单 - vX.Y.Z / StageN

## 置顶区（待用户确认，阻塞开发）

> 本区问题必须由用户明确答复后才能进入开发或下一 Stage。

### Q1. 问题标题
- **问题描述**：定位到具体文件/模块/行号，明确不确定点。
- **建议方案**：...
- **备选方案**：方案 A / 方案 B ...
- **风险预警**：...
- **置信度**：例如 70%
- **归入置顶原因**：例如"两种方案对后续扩展性影响差异较大，需用户拍板"或"涉及硬件协议不可逆决策"。

## 自决区（≥ 90% 置信，已自决，不阻塞开发）

> 本区问题由 MainAgent 自主决策，用户可随时否决或提出异议，但不阻塞当前开发流程。

### Q2. 问题标题
- **问题描述**：...
- **自决方案**：...
- **自决理由**：例如"Python reference `src/device_center/protocol.py:123` 已有明确实现，直接对齐"。
- **风险预警**：...
- **置信度**：例如 95%
```

**审核自检问题：**

- 每个问题是否都附带建议方案或说明？
- 是否为每个问题给出了置信度评估？
- 建议方案是否优先考虑鲁棒性和可测试性，而不是开发速度？
- 风险预警是否覆盖可能导致 Stage 中断或 Version 无法闭环的情形？
- 置顶区是否只包含真正需要用户决策的问题？（避免把 MainAgent 有把握的问题都推给用户）
- 自决区是否给出了充分的"自决理由"？（避免用置信度虚高来绕过用户决策）
- 用户仅凭置顶区问题能否做出"同意建议 / 否决并说明理由 / 选择备选方案"的判断？

**禁止事项：**

- 禁止提出无建议的开放式裸问题。
- 禁止把多个相互独立的问题塞进一条问题中。
- 禁止在建议中省略风险。
- 禁止以"为了赶工""实现成本低""看起来简单优雅"作为建议方案的核心理由。
- **禁止不写入问题清单直接开发**（即使 100% 有把握，也必须落到自决区，保证可追溯性）。
- **禁止把 MainAgent 明显有把握的问题（≥ 90% 置信且无路线分歧）塞进置顶区打扰用户**；反之，**禁止把有明显路线分歧或低置信度的问题塞进自决区**跳过用户决策。

#### 6.3 “零上下文可验收”标准

> **核心要求：任何 Stage/Version 验收文档，都必须让一个全新的 Agent 或验收者在没有对话历史、没有口头说明的情况下，独立判断交付是否通过。**

这是验收质量的强制门禁。验收文档必须在开发前准备好，避免开发完成后再临时补标准。

**必须包含的内容：**

1. **验收范围**：明确本次验收覆盖哪些功能、文件、模块、业务路径，以及不覆盖哪些内容。
2. **验收环境**：列出操作系统、构建配置、测试数据、硬件依赖、外部服务、账号权限、设备连接方式等。
3. **前置条件**：说明验收开始前仓库、配置、数据、设备或应用状态必须满足什么条件。
4. **验收项列表**：每条验收项必须有唯一编号、目的、操作步骤、期望结果、通过/失败标准。
5. **证据要求**：说明每条验收项需要保留什么证据，例如命令输出、生成文件路径、日志片段、截图说明、人工观察记录。
6. **失败与阻塞处理**：定义失败如何记录、何时重试、何时追加问题清单、何时退回开发。
7. **回归范围**：说明哪些历史功能需要回归，哪些只需冒烟测试，哪些明确不在本次验收范围。
8. **交付物检查**：列出必须存在且内容完整的文档、测试报告、完成报告、配置文件或样例数据。

**验收项推荐格式：**

```markdown
### A1. 验收项标题

- **目的**：说明该项验证什么风险或需求。
- **前置条件**：开始该项前必须满足的状态。
- **操作步骤**：逐步写清楚命令、点击路径、输入数据或文件路径。
- **期望结果**：可观察、可判断、不可依赖主观猜测。
- **通过标准**：满足哪些条件即为通过。
- **失败标准**：出现哪些现象即为失败。
- **证据要求**：需要记录的输出、文件、日志或截图说明。
```

**审核自检问题：**

- 一个未参与开发的新 Agent，能否仅凭验收文档执行验收？
- 每条验收项是否都有明确操作步骤和期望结果？
- 是否存在“检查是否正常”“确认无问题”等主观表述？有则必须改成可观察标准。
- 验收环境和前置条件是否足够明确？
- 失败、阻塞、无法执行时是否有明确处理方式？
- 验收证据是否足以支撑完成报告中的结论？

**禁止事项：**

- 禁止用“按之前讨论验收”“看起来正常即可”等依赖上下文的描述。
- 禁止只有测试命令而没有期望输出或失败处理。
- 禁止把无法执行的硬件/人工验收项默认为通过。
- 禁止在开发完成后才第一次定义核心验收标准。

### 7. 适用范围与限制

- ✅ 本范式专用于大规模 Version：需求点数量 ≥ 5，存在明显可并行子任务，或代码依赖复杂。
- ✅ 小规模 Version 可不拆 Stage/SubStage，但仍必须遵守问题清单、置信度分级、零猜测和零上下文验收原则。
- ✅ 大规模 Version 的 Stage 设计文档必须满足"零上下文可开发"。
- ✅ 大规模 Version 的 Stage/Version 验收文档必须满足"零上下文可验收"。
- ⚠️ MainAgent 必须具备较强的任务分解、依赖分析、接口契约设计和验收设计能力。
- ⚠️ 如果代码耦合度过高，无法拆分为无依赖 SubStage，则优先重构解耦，否则该范式效果会大打折扣。
- ⚠️ SubAgent 之间零沟通，所有协作必须上升至 MainAgent 协调，这会增加 MainAgent 的设计负担，但能避免阻塞和混乱。
- ⚠️ 问题清单是强制门禁：**置顶区**未关闭所有问题前不允许进入实际开发或验收；**自决区**问题不阻塞流程但必须完整记录。
- ⚠️ 验收文档是强制门禁：验收标准不清时，不允许把交付判定为完成。
- ⚠️ 启动测试是强制门禁（新功能/较大更新）：未跑通启动测试或未在完成报告中提供启动测试证据/豁免说明前，不允许将 Stage 或 Version 判定为完成。

### 8. 推荐目录结构

大规模 Version 建议使用以下目录结构：

```text
Document/Update/vX.Y.Z - 版本名称/
├── 需求文档.md
├── 问题清单.md
├── 验收文档.md                 # Version 级验收
├── 总结报告.md                 # Version 完成后生成
├── Stage1/
│   ├── 问题清单.md
│   ├── 设计文档.md
│   ├── 验收文档.md
│   └── 完成报告.md
├── Stage2/
│   ├── 问题清单.md
│   ├── 设计文档.md
│   ├── 验收文档.md
│   └── 完成报告.md
└── StageN/
    ├── 问题清单.md
    ├── 设计文档.md
    ├── 验收文档.md
    └── 完成报告.md
```

如果某个 Stage 很小，验收文档可以作为 `设计文档.md` 的独立章节存在；但只要存在多个 SubStage、硬件依赖、外部系统依赖或人工验收步骤，必须拆成独立 `验收文档.md`。
